# Архитектура Pause Hold И Pause Empty

Дата: `2026-04-08`

## Назначение

Этот документ фиксирует новый базовый pause-контракт для `version_5`.

Он заменяет рабочую интуицию вида:

- `COMMON PAUSE` обязательно должен любой ценой сделать полностью пустую линию;
- мастер сам догадывается о финале паузы только по coarse-битам normal-cycle.

Для `version_5` принимается более явная модель:

- `COMMON PAUSE` сначала должен приводить линию к детерминированному `pause_hold`;
- `pause_empty` остается отдельным, более строгим режимом;
- если ни `pause_hold`, ни `pause_empty` автоматически недостижимы, система должна честно переходить в `manual recovery required`.

## Актуализация На `2026-04-09`

На текущий момент этот документ остается правильной целевой архитектурой, но по стенду уже есть важные уточнения:

- межузловой scaffold
  `pause request -> node prepare/ready -> finalize`
  уже подтвержден;
- silent hang в `pause_fill_last_block` больше не считается допустимым поведением;
- если после `pause_finalize` мастер видит, что честный `pause_hold` недостижим, он должен быстро давать явный terminal outcome, а не висеть до watchdog timeout.

Что уже подтверждено на стенде:

- `COM10` переведен на safe-boundary pause-логику и больше не должен рвать `P1/C2` посередине;
- `COM11` входит в pause-сценарий через явный prep/runtime-контур;
- `COM12` умеет доходить до terminal outcome без silent hang.

Что еще не закрыто:

- production-цель `pause_empty` пока не подтверждена;
- на реальном прогоне `2026-04-09` линия пришла к честному
  `manual_recovery_required`,
  но физически на линии остались тарелки;
- дополнительно зафиксировано расхождение между физическим остатком и тем,
  как `COM12` оценивает `buffer_count / sealer_count` в terminal decision.

Практический вывод для `version_5`:

- silent hang уже не является допустимым исходом;
- честный `manual_recovery_required` допустим как промежуточный production-safe финал;
- но шаг `COMMON PAUSE` нельзя считать полностью закрытым, пока не будет согласован один из двух вариантов:
  - линия реально приходит к `pause_empty`;
  - или архитектурно принят `pause_hold` с честным и подтвержденным residual accounting, совпадающим с механикой.

## Короткое Решение

Целевой контракт:

1. Оператор подает `COMMON PAUSE`.
2. Master ставит глобальный `pause latch`.
3. После этого новые normal-start запрещены.
4. Master переводит узлы в явный `pause-mode`.
5. Узлы работают уже не по правилам обычного `COMMON`, а по отдельным pause-правилам.
6. Финал должен быть только один из трех:
   - `pause_hold`
   - `pause_empty`
   - `manual_recovery_required`

## Главное Разделение

### `pause_hold`

Это основной целевой режим для `version_5`.

Смысл:

- линия остановлена детерминированно;
- новые normal-start не идут;
- остатки на линии допустимы только в заранее известных местах;
- оператор и мастер знают, сколько контейнеров где осталось.

Дополнительное правило `version_5`:

- `pause_hold` допустим только как `known residual hold`;
- это значит, что остатки не просто "есть", а:
  - локализованы в заранее разрешенных местах;
  - имеют валидные counts;
  - помечены как `residual_known = true`.

Отдельное уточнение по результатам стенда:

- `pause_hold` нельзя подтверждать только потому, что runtime перестал двигаться;
- `pause_hold` допустим только если residual accounting мастера совпадает с фактической механикой линии.

### `pause_empty`

Это более строгий режим.

Смысл:

- линия полностью пустая;
- на запайщике нет контейнеров;
- в буфере двухручейкового подвода нет контейнеров;
- хвост полностью выгружен.

Для `version_5` `pause_empty` не запрещается, но не должен оставаться единственным допустимым исходом pause-контракта.

### `manual_recovery_required`

Смысл:

- автоматический честный финал паузы не достигнут;
- безопасно продолжать автоматикой нельзя;
- дальнейшие действия идут только через явный recovery-сценарий.

## Что Делает Master

После `COMMON PAUSE` master должен:

- поставить глобальный `pause latch`;
- запретить новые normal-start:
  - новый `P1`;
  - новый normal манипуляторный цикл;
  - новый normal continuation поверх pause;
- перевести узлы в явный `pause-mode`;
- ждать не "случайного набора битов", а явных pause-статусов узлов;
- фиксировать один итог:
  - `pause_hold`
  - `pause_empty`
  - `manual_recovery_required`

Дополнительно master должен:

- вести отдельный `pause_epoch` / `pause_cycle_id` для текущего pause-сценария;
- принимать `PAUSE STATUS` узлов только как часть согласованного snapshot этого `pause_epoch`;
- не подтверждать `pause_hold` или `pause_empty`, если counts или pause-status какого-либо узла stale / invalid;
- держать watchdog прогресса для `pause_arming`;
- при отсутствии прогресса эскалировать в `manual_recovery_required`.

Master не должен:

- после `COMMON PAUSE` продолжать обычную логику как будто паузы нет;
- бесконечно крутиться между промежуточными pause-state;
- молча зависать без финального pause outcome;
- объявлять пустую безопасную линию, если на линии еще есть контейнеры.
- разрешать `PAUSE RELEASE` как скрытый resume старого контекста.

## Команды

### Внешние Команды Master

- `COMMON PAUSE`
  Ставит глобальный pause latch и запускает pause-контракт.

- `COMMON PAUSE STATUS`
  Возвращает текущий глобальный pause-state и остатки по линии.

- `COMMON PAUSE RELEASE`
  Снимает pause-mode после честного `pause_hold` или `pause_empty`.
  Не возобновляет старый цикл.
  После него допустим только новый `COMMON START` с новым `cycle_id`.

- `COMMON PAUSE EMPTY`
  Отдельный будущий режим.
  Не считать обязательным первым этапом `version_5`.

### Внутренние Команды Master -> Узлы

Минимальный набор:

- `PAUSE ARM`
  Узел прекращает normal-start и переходит на pause-правила.

- `PAUSE STATUS`
  Узел возвращает свой local pause-state и нужные операторские counts.
  Ответ должен содержать `pause_epoch` и флаги валидности counts.

- `PAUSE RELEASE`
  Узел выходит из pause-mode обратно в normal ready/wait.

Recovery-команды не смешивать с pause-командами:

- pause не равен аварии;
- recovery-clear должен оставаться отдельным контрактом.

## Pause-Контракт По Узлам

### Подводящий Блок

Локальная цель:

- перестать подбрасывать новые тарелки в буфер "по инерции";
- собрать остаток только до pause-ограничения;
- прийти к known hold-state.

Правила:

- перед пропуском тарелок в буфер проверять, что хотя бы одна линия двухручейкового подвода свободна;
- если обе линии заняты, больше не пропускать тарелки в буфер;
- если двухручейковый подвод уже заполнен до pause-формы и буфер пуст, подводящий блок = `pause_hold`.

Для `version_5` это значит:

- `buffer_count = 0` является обязательным условием для честного hold по подводящему блоку;
- partial buffer не должен маскироваться под "ждем еще один normal batch".
- если `buffer_count` unknown / stale, `pause_hold` подтверждать нельзя.
- если `buffer_count > 0` и нового полного batch уже не будет, runtime не должен висеть молча;
  он обязан быстро перейти в явный terminal outcome.

### Манипулятор

Локальная цель:

- завершить только разрешенный pause-tail;
- не стартовать новый normal-cycle;
- перейти в known hold-state.

Правила:

- ждать, пока подводящий блок достигнет `pause_hold`;
- после этого сделать один завершающий такт;
- если на запайщике остается уже запаянный блок, сделать еще один завершающий такт;
- затем перейти в `pause_hold`.

### Запайщик

Локальная цель:

- перестать быть частью normal-cycle;
- удерживать известный остаток, если он есть;
- честно сообщать, пуст он или нет.

Правила:

- если на нем есть уже запаянные контейнеры и upstream уже в pause, запайщик тоже переходит в `pause_hold`;
- `pause_hold` для запайщика не означает автоматически `empty`;
- если требуется действительно пустой запайщик, это уже цель `pause_empty`.

Для `version_5` это значит:

- `sealer_count > 0` допустим в `pause_hold` только если:
  - `sealer_count_valid = true`
  - `residual_known = true`
  - UI явно показывает остаток как known residual.
- если физически тарелки на запайщике остались, а `sealer_count` у мастера говорит `0`,
  это считать отдельным production-дефектом residual accounting, а не приемлемым вариантом `pause_hold`.

### Отводящий Блок

Локальная цель:

- либо честно опустеть;
- либо честно показать, что empty не достигнут.

Правила:

- если отвод пустой и манипулятор уже в паузе, отводящий блок переходит в `pause_hold`;
- если empty автоматически недостижим, нужен честный `manual_recovery_required`, а не молчаливое ожидание.

## Обязательные Pause-Статусы

Каждый узел должен уметь вернуть:

- `pause_state = none`
- `pause_state = arming`
- `pause_state = hold`
- `pause_state = empty`
- `pause_state = manual_recovery_required`

Дополнительно нужны:

- `pause_epoch`
- `pause_reason`
- `can_release_pause`
- `manual_recovery_required`
- `progress_observed`

## Обязательные Counts Для Оператора И Master

Минимальный набор:

- `buffer_count`
- `dual_lane_count` или эквивалентный coarse-count по двухручейковому подводу
- `sealer_count`
- `outfeed_count` или `outfeed_empty`

Для каждого count также нужны:

- `*_count_valid`
- `*_count_fresh`
- при необходимости единый `counts_epoch`

Главный смысл:

- мастер и оператор должны видеть не только `busy/ready`, но и сколько контейнеров реально осталось на линии.
- invalid / stale counts не могут подтверждать `pause_hold` или `pause_empty`.

## Watchdog `pause_arming`

`pause_arming` не может быть бесконечным состоянием.

Нужен обязательный контракт:

- есть стартовая точка `pause_arming_since_ms`;
- есть признак прогресса pause-контракта;
- есть таймаут;
- есть эскалация в `manual_recovery_required`, если:
  - нет прогресса;
  - нет валидного snapshot узлов;
  - финальный честный outcome недостижим.

Примеры допустимого прогресса:

- один из узлов перешел в новый pause-state;
- `buffer_count` уменьшился;
- `sealer_count` уменьшился;
- появился валидный pause-snapshot нужного `pause_epoch`.

## Инварианты

- после `COMMON PAUSE` новые normal-start запрещены;
- `pause_hold` не равен `pause_empty`;
- `pause_hold` допустим только с известными остатками;
- `buffer_count > 0` не должен считаться честным финалом pause-контракта;
- invalid / stale counts не должны считаться честным финалом pause-контракта;
- если детерминированный pause-финал недостижим, нужен `manual_recovery_required`;
- `COMMON PAUSE RELEASE` допустим только после честного `pause_hold` или `pause_empty`;
- `COMMON PAUSE RELEASE` не продолжает старый цикл и не восстанавливает старый `stage/seq/tail`;
- `manual recovery` не должен маскироваться под обычную паузу.

## Что Должно Видеть Web UI

UI должен явно показывать:

- глобальный pause-mode:
  - `arming`
  - `hold`
  - `empty`
  - `manual recovery required`
- валидность/свежесть counts;
- сколько контейнеров осталось:
  - на запайщике;
  - в буфере двухручейкового подвода;
- какие узлы уже в `pause_hold`;
- какие узлы еще в `pause-drain`;
- когда release допустим, а когда нужен recovery.

UI не должен:

- подписывать `pause_hold` как "линия пуста", если это не так;
- подтверждать `pause_hold` или `pause_empty`, если counts stale / invalid;
- прятать остатки контейнеров;
- смешивать `pause` и `manual recovery`.

## Что Нуждается В Независимом Review

Перед реализацией и после реализации отдельно проверить:

- действительно ли `pause_hold` лучше соответствует реальной механике, чем старое требование `empty-by-default`;
- не создаст ли `pause_hold` скрытый unsafe хвост;
- достаточно ли одного/двух завершающих тактов манипулятора;
- можно ли считать `buffer_count = 0` обязательным, но `sealer_count > 0` допустимым в hold;
- как именно формализовать `residual_known = true`;
- где проходит граница между `pause_hold` и `manual_recovery_required`;
- не превратится ли `COMMON PAUSE RELEASE` в скрытый auto-resume неявного старого цикла.
