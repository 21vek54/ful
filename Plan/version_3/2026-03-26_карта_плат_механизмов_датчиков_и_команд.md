# Карта плат, механизмов, датчиков и локальных команд

Дата: 2026-03-26

## Назначение

Этот документ фиксирует единый словарь `version_3`:
- какие платы реально есть в проекте;
- какие исполнительные механизмы и датчики на них уже существуют;
- какими именами они названы в коде и в wiring-документации;
- какие локальные команды на платах уже есть;
- что уже существует на уровнях `I2C`, `MQTT` и `Node-RED`.

Документ нужен как промежуточный слой между:
- архитектурой;
- будущим разделением `CMD1 / CMD2`;
- будущим контрактом `I2C`;
- будущим контрактом `MQTT`;
- будущей структурой `Node-RED`.

## Важное допущение

Ниже считаем, что в обсуждении имеется в виду `I2C`, а не `I2S`, потому что в текущем проекте межплатный статусный контур уже построен именно на `I2C`:
- `conveyor_control_com10` — адрес `12`;
- `manipulator_com11` — адрес `13`.

## Решения на текущем этапе

- Сначала фиксируем физический состав системы и локальные имена.
- Не смешиваем локальные сервисные команды плат и будущие системные `CMD1 / CMD2`.
- Сначала строим словарь `механизм -> датчик -> локальная команда -> локальный статус`, потом поверх него проектируем `I2C`, потом `MQTT`, потом `Node-RED`.
- `master_control_com12` в этом документе рассматривается как агрегатор и транспорт, а не как владелец полевой физики.

## Платы и роли

| Плата | Прошивка | Адрес / роль в обмене | Назначение |
|---|---|---|---|
| Конвейер | `firmware/conveyor_control_com10` | `I2C slave addr 12`, `deviceKind=1` | Локальная логика конвейерной части, отвода и запайщика |
| Манипулятор | `firmware/manipulator_com11` | `I2C slave addr 13`, `deviceKind=2` | Локальная механика манипулятора, ручной режим, цикл, recovery |
| Мастер | `firmware/master_control_com12` | `I2C master`, `MQTT publisher` | `Wi-Fi + MQTT + I2C` и агрегация статусов |

## Граница ответственности по командам

- Локальные команды платы — это текущий инженерный интерфейс самой платы.
- Будущие `CMD1` — это мастер-уровень для атомарных действий, а не копия всех локальных debug-команд.
- Будущие `CMD2` — это завершённые операции уровня мастера.
- `Node-RED` не должен отправлять в оператора сырой набор всех локальных сервисных команд без отдельного архитектурного решения.

### Текущие локальные группы команд

- Основной конвейер: `D`, `MAINSTART`, `MAINSTOP`, `1`, `2`
- Позиционный участок: `3`, `P`, `POSSTART`, `POSSTOP`
- Сдвиг: `C`, `Z`, `CZ`
- Флаг: `W`, `S`
- Отвод и `STEP2`: `T2`, `STEP2`, `OTVOD`, `STEP2START`, `STEP2STOP`, `STOP2`, `OTCYCLE START|STATUS|STOP`
- Частотник: `R1ON`, `R1OFF`, `VFD5MIN`, `VFDSTOP`, `VFDTICK SHOW|RUN|TEST|SAVE`
- Запайщик: `SEAL START`, `SEAL STATUS`, `SEAL OUT ON|OFF`
- Сервис: `E`, `H`

Важно:
- это локальные команды платы;
- они полезны как источник для будущего контракта;
- они не должны автоматически считаться будущими операторскими командами `CMD1 / CMD2`.

### Что уже есть на уровне `I2C`

Конвейер уже поднимает статусный кадр:
- `addr = 12`
- `magic = 0x4659`
- `protoVer = 1`
- `deviceKind = 1`
- размер кадра `28` байт

Содержимое кадра:
- `statusWord`
  - `bit0` = ready
  - `bit1` = busy
  - `bit2` = safe
  - `bit3` = alarm
  - `bit4` = calibrated
  - `bit5` = `program1 active`
  - `bit6` = `batch ready`
  - `bit7` = `step2 active`
  - `bit8..15` = `step2 completion seq`
- `errorWord`
  - `bit0` = `sensor conflict`
  - `bit1` = `not calibrated`
- `extra0`
  - младший байт = состояние флага: `1=DOWN`, `2=UP`
  - старший байт = состояние движения: `0=IDLE`, `1=RUNNING`, `2=POSITIONING`
- `extra1`
  - длительность `VFD tick` в единицах `10 ms`
- `extra2`
  - `program1 state code` в младшем байте
  - `program1 pass index` в старшем байте
- `extra3`
  - младшие `15` бит = `batchReadySequence`
  - `bit15` = `batchReadyForManipulator`

Также уже есть `I2C`-канал управляемого текста:
- `opcode 0xA5` = `poke`
- `opcode 0xA6` = текстовая команда
- длина текстовой команды до `64` байт

На текущем этапе это считать сервисным техническим слоем, а не финальным операторским API.

### Что уже есть на уровне `I2C`

Манипулятор уже поднимает статусный кадр:
- `addr = 13`
- `magic = 0x4659`
- `protoVer = 1`
- `deviceKind = 2`
- размер кадра `28` байт

Содержимое кадра:
- `statusWord`
  - `bit0` = ready
  - `bit1` = busy
  - `bit2` = safe
  - `bit3` = alarm
  - `bit4` = calibrated
  - `bit5` = `step7 ready`
- `errorWord`
  - `bit0` = `driver alarm`
  - `bit1` = `limits conflict`
  - `bit2` = `Z conflict`
  - `bit3` = `grip conflict`
  - `bit4` = `not calibrated`
- `extra0`
  - `mode code`: `1=idle`, `2=busy`, `3=error`
- `extra1`
  - `job code`: `0=none`, `1=work`, `2=test`, `3=grease`, `4=calib`, `5=manual`
- `extra2`
  - биты датчиков:
    - `bit0` = left limit
    - `bit1` = right limit
    - `bit2` = `Z up`
    - `bit3` = `Z down`
    - `bit4` = grip open
    - `bit5` = grip closed
    - `bit6` = driver alarm
- `extra3`
  - младший байт = конфликты:
    - `bit0` = both limits
    - `bit1` = `Z conflict`
    - `bit2` = grip conflict
  - старший байт = `work cycle current step`

Также уже есть `I2C`-канал управляемого текста:
- `opcode 0xA5` = `poke`
- `opcode 0xA6` = текстовая команда
- длина текстовой команды до `64` байт

На текущем этапе это тоже считать сервисным техническим слоем, а не готовым операторским API.

## Мастер `master_control_com12`

### Текущая роль

Сейчас мастер реально отвечает за:
- `Wi-Fi`
- `MQTT`
- `I2C`-опрос плат `12` и `13`
- публикацию минимального агрегированного статуса

Текущие `I2C`-идентификаторы:
- `CONVEYOR_ID = 12`
- `MANIPULATOR_ID = 13`

### Текущий `MQTT`-контур

Базовый топик мастера:
- `fyl/master_com12`

Реально работающие топики на 2026-03-26:
- `fyl/master_com12/status`
- `fyl/master_com12/online`

Содержимое `status` сейчас минимальное:
- `wifi`
- `mqtt`
- `board12`
- `board13`

Топики:
- `cmd`
- `resp`
- `event`

пока не открыты как рабочий слой `version_3`.

### Текущий `Node-RED`

Текущий dashboard опирается именно на:
- `fyl/master_com12/status`
- `fyl/master_com12/online`

То есть сейчас `Node-RED` уже работает как `HMI` minimal-контура, но ещё не опирается на полноценный словарь механизмов, датчиков и команд.

## Что принимаем как решение уже сейчас

- Основным именованием во внешних документах считать сначала смысловое имя узла, потом имя в коде.
- `GPIO` и локальные CLI-команды не должны напрямую становиться UI-лексикой оператора.
- Локальные команды нужны как инженерный и переходный слой, но финальный контракт `CMD1 / CMD2` должен строиться отдельно.
- Цепочка проектирования для `version_3` должна быть такой:
  - физический узел и датчик;
  - локальная плата и её статусы;
  - `I2C`-кадр и служебный командный канал;
  - модель мастера;
  - `MQTT`-контракт;
  - `Node-RED`-экран.

## Что этот документ пока не решает

- окончательное разделение `CMD1 / CMD2`;
- окончательный текстовый контракт команд мастера;
- окончательный набор `MQTT topics`;
- окончательную структуру вкладок и кнопок в `Node-RED`;
- какие именно локальные команды будут доступны оператору, а какие останутся только сервисными.

## Следующий пакет документации

После этого документа логично делать так:

1. Отдельно зафиксировать словарь состояний и имён узлов для модели мастера.
2. Отдельно зафиксировать, какие данные из этой карты должны попасть в `I2C`.
3. Отдельно зафиксировать, какие команды из этой карты могут стать `CMD1`.
4. Отдельно зафиксировать, какие операции могут стать `CMD2`.
5. Только после этого описывать `MQTT` и затем `Node-RED`.
