# Ревизия плана 1: что сделано и что нет

Дата: 2026-03-26

## Какой план ревизуем

За основной "план 1" в этой ревизии принят файл:
- `Plan/version_1/2026-03-21_step_by_step_plan.md`

Он лучше всего подходит для статуса, потому что разбит на последовательные этапы.
Файл `2026-03-21_migration_plan.md` по смыслу ему соответствует и не противоречит этой ревизии.

## Важная оговорка

Ниже статус дан не только "по памяти", а по текущим файлам проекта и по тому, что реально осталось в рабочем контуре после перехода на минимальный `master_control_com12`.

Поэтому здесь различаем:
- `сделано`
- `частично сделано`
- `не сделано`
- `соблюдено как ограничение`

## Статус по этапам

### Этап 0. Зафиксировать текущую рабочую базу
Статус: `сделано`

Почему:
- есть архив планов `version_1`;
- есть инвентаризация перед reset;
- есть runtime backup перед сбросом;
- рабочие решения были сохранены до чистки мастера.

Опорные файлы:
- `Plan/version_1/2026-03-24_stack_inventory_before_reset.md`
- `Plan/version_1/runtime_backup_2026-03-24`

### Этап 1. Утвердить новую архитектуру по ролям
Статус: `сделано`

Почему:
- архитектура "конвейер = полевая логика, мастер = координатор, Node-RED = интерфейс" была принята и дальше использовалась;
- все последующие шаги `version_2` и текущий minimal `master` строились уже из этой роли.

### Этап 2. Утвердить минимальный набор новых физических сигналов
Статус: `сделано`

Почему:

Почему:

- есть wiring и pinout под сухой пуск частотника с платы конвейера;

Опорные файлы:

### Этап 4. Перенести сигналы запайщика на плату конвейера
Статус: `сделано`

Почему:
- в проекте конвейера есть отдельная группа запайщика;
- wiring и pinout уже опираются на локальный старт запайщика и вход `цикл завершен` на конвейерной плате;
- master в текущем минимальном варианте не держит эту проводную физику на себе.

Опорные файлы:
- `firmware/conveyor_control_com10/docs/conveyor_wiring.md`

### Этап 5. Довести плату конвейера до роли главного полевого узла
Статус: `сделано`

Почему:
- в конвейерной прошивке есть отдельные группы `infeed`, `outfeed`, `sealer`;
- плата конвейера уже выглядит как единый полевой узел конвейерной части, а не как набор разрозненных кусков.

Оговорка:
- после reset текущий `master` использует только минимальный слой `online/offline`, поэтому богатая полевая модель не вся задействована в текущем runtime.

Опорные файлы:

## Что важно помнить дальше

Ощущение "дошли до пункта 8" частично понятно, потому что до reset были сильные наработки по модели, интерфейсу и общей логике.
Но по текущему состоянию проекта правильно считать так:

- ранняя архитектурная и полевая часть была реально продвинута далеко;
- затем был осознанный reset в сторону минимального `master`;
- поэтому этапы про модель зон, новый общий цикл и recovery нужно считать не закрытыми, а перенесенными в следующий цикл развития.
