# Архитектурная основа

Дата: 2026-03-26

## Назначение

Этот документ фиксирует базовые архитектурные решения проекта.
Он нужен как опорный контекст для планов, реализации и ревизий.

При пере-реализации проекта этот документ нужно не игнорировать, а дорабатывать.
Если меняется архитектурная роль узла, контракт команд или модель линии, изменения сначала должны быть отражены здесь.

Организация работы с ИИ-агентами вынесена в отдельный файл:
- `Plan/Процесс_разработки_с_ИИ.md`

Этот документ не должен смешивать архитектуру линии и процесс разработки.

## Базовые роли системы

### `Node-RED`

`Node-RED` — это операторский интерфейс (`HMI`), а не мозг линии.

Он должен:
- показывать состояние линии и устройств;
- позволять оператору отправлять команды;
- использоваться для инициализации и восстановления после аварий.

Он не должен:
- хранить автоматику линии;
- принимать технологические решения вместо мастера;
- превращаться в скрытый контроллер.

### Мастер и контроллеры

Вся реальная логика, автоматические решения и выполнение последовательностей должны жить:
- в мастере;
- или в профильных контроллерах.

`Node-RED` только показывает, отправляет команду и отображает результат.

При этом мастер не обязан владеть каждой внутренней механической последовательностью.
Если у профильного контроллера есть локальный законченный технологический участок, допустимо оформлять его как отдельный high-level контракт этого контроллера.

Пример такого решения:
- `MASTER` работает с `COM10` через high-level команды `POST7 START LOAD`, `POST7 START UNLOAD_ONLY`, `POST7 STOP`;
- внутреннюю локальную orchestration `SEALER + OUTFEED` выполняет сам `COM10`;
- мастер в таком случае остается координатором верхнего уровня, а не владельцем каждой raw-команды внутри локального узла.

Это правило нужно, чтобы граница ответственности проходила по законченной технологической операции, а не по случайному набору низкоуровневых стартов.

## Базовая структура интерфейса

Операторский интерфейс версии 3 должен быть разбит минимум на 4 вкладки:

1. Мониторинг плат
2. Команды 1 уровня
3. Команды 2 уровня
4. Инициализация и восстановление

### 1. Мониторинг плат

Здесь только:
- связь;
- heartbeat;
- базовые статусы;
- без управления.

### 2. Команды 1 уровня

Это атомарные ручные действия:
- одно нажатие;
- одно простое действие;
- без технологической логики;
- для наладки и ручной отладки.

Примеры:
- `CMD1 MANIP GRIP OPEN`
- `CMD1 INFEED STEP`
- `CMD1 IN2 STEP`
- `CMD1 SEAL CLAMP CLOSE`

### 3. Команды 2 уровня

Это завершённые операции:
- могут включать последовательность действий;
- исполняются мастером;
- `Node-RED` только отправляет команду и показывает результат.

Часть команд 2 уровня может исполняться не только мастером, но и профильным контроллером, если этот контроллер владеет соответствующим локальным технологическим участком.

В таком случае:
- мастер или `Node-RED` отправляет high-level команду;
- профильный контроллер сам выполняет внутреннюю последовательность;
- наружу отдает coarse-статус завершения, занятости и аварии.

Примеры:
- `CMD2 BUILD IN2 6`
- `CMD2 CYCLE START_MAIN`
- `CMD2 INIT ALL`

### 4. Инициализация и восстановление

Это отдельный режим:
- ручная установка состояния линии;
- подтверждение модели после аварии;
- редактирование зон;
- подтверждение и сброс состояния.

## Базовая модель линии

### Двухручейковые узлы

Двухручейковые узлы нельзя описывать только грубо как `лево / право`.

Для версии 3 нужно хранить и показывать точную структуру:
- `IN2.LINE1`
- `IN2.LINE2`
- `IN2.LINE3`
- `OUT2.LINE1`
- `OUT2.LINE2`
- `OUT2.LINE3`

Для каждой линии нужно хранить минимум одно из состояний:
- `EMPTY`
- `OCCUPIED`
- `UNKNOWN`

Для оператора это должно отображаться русскими подписями:
- `Пусто`
- `Занято`
- `Неизвестно`

Эта модель нужна для:
- понятного отображения линии;
- корректного восстановления после аварии;
- точной внутренней модели у мастера.

## Разделение команд

### Команды 1 уровня

Команды 1 уровня:
- атомарные;
- без логики;
- для ручной отладки.

### Команды 2 уровня

Команды 2 уровня:
- завершённые операции;
- могут включать последовательности;
- исполняются мастером.

Допустимое расширение:
- если локальной последовательностью владеет профильный контроллер, команда 2 уровня может исполняться на нем, а не внутри мастера;
- мастер в таком случае координирует узлы по coarse-контракту, а не по внутренним микрошагам соседнего контроллера.

### Команды инициализации модели

Примеры:
- `CMD2 LINESTATE SET IN2 LINE1 OCCUPIED`
- `CMD2 LINESTATE SET OUT2 LINE3 EMPTY`
- `CMD2 LINESTATE CONFIRM`

## Главный архитектурный принцип

Нельзя переносить автоматику линии в `Node-RED`.

Если интерфейс:
- начинает сам исполнять последовательности;
- держит технологические переходы;
- принимает логические решения вместо мастера,

значит архитектура начала ломаться.

Дополнительный архитектурный принцип:

- мастер должен знать только те состояния и команды, которые реально нужны для координации между узлами;
- внутренние промежуточные фазы локального узла должны по возможности оставаться внутри профильного контроллера;
- наружу нужно выносить только coarse-контракт уровня `ready / busy / completed / alarm / recovery required`, если этого достаточно для координации линии.

Это особенно важно для recovery-сценариев:
- production-visible interlock допустимо поднимать как coarse fault узла;
- сервисное восстановление может оставаться отдельной доверенной операторской процедурой;
- не нужно без сильной причины раздувать межплатный контракт ради внутренних микрофаз механики.
