# Промт для кодера: доработка после ревью строгого пути

Дата: 2026-03-31

### Назначение

Этот текст нужен для передачи кодеру точечных доработок после ревью реализации строгого пути `version_4`.

Главный смысл:

- архитектурная модель `version_4` остается целевой;
- ревью уже нашло блокирующие места;
- сейчас не нужно заново пересобирать всю архитектуру;
- нужно убрать конкретные блокеры и не ослабить модель.

## Контекст

По результатам ревью подтверждено:

- `step3_ready` сделан как отдельный runtime-latch в прошивке манипулятора;
- `step3_ready` выведен отдельным битом в `statusWord` по `I2C`;
- `step7_ready` сохранен как latch и верхний уровень использует его относительно безопасно.

Но найдены блокирующие замечания:

1. `pause_stable_wait` может выставляться без явной гарантии `SEALER = EMPTY`.
2. `feed_side_empty` в верхней логике реализован упрощенно и не соответствует строгому определению `version_4`.
3. recovery-ветка может оставлять `step3_ready = 0`, даже когда при продолжении цикла правая сторона уже фактически освобождена.

## Готовый промт

```text
Ты дорабатываешь реализацию строгого пути `version_4` после код-ревью.

Сначала прочитай:
1. `PLSN.md`
2. `Plan/основной_цикл.md`
3. `Plan/сущности_и_состояния.md`
4. все файлы из `Plan/version_4/`
5. `firmware/manipulator_com11/src/work_cycle.h`
6. `firmware/manipulator_com11/src/work_cycle.cpp`
7. `firmware/manipulator_com11/src/main_10.inc`
8. `archive/firmware/master_control_com12_legacy_2026-03-25/src/master_main.cpp`

Твоя роль:
- ты не перепридумываешь модель;
- строгий путь `version_4` уже остается целевым;
- нужно убрать блокеры, найденные на ревью;
- нельзя ослаблять модель ради быстрого прохождения ревью.

Что нужно исправить обязательно:

1. Исправить переход в `pause_stable_wait`

Проблема:
- сейчас верхняя логика может прийти в `pause_stable_wait` без явной гарантии `SEALER = EMPTY`.

Что требуется:
- перед установкой `pauseState = StableWait` добавить явное подтверждение, что `SEALER` действительно пуст;
- если `SEALER` еще не пуст, линия не имеет права переходить в “чистую паузу”;
- в таком случае нужно оставаться в корректной паузной ветке ожидания, а не выдавать ложный финал;
- решение должно соответствовать инварианту `pause_stable_wait` допустим только при `SEALER = EMPTY`.

2. Исправить контракт `feed_side_empty`

Проблема:
- сейчас `feed_side_empty` в верхней логике упрощен до двух косвенных флагов;
- это не эквивалент строгому определению `version_4`.

Строгое определение:
- `BUFFER_COUNT = 0`
- `SHIFT = HOME_Z`
- `IN2.LINE1 = 0`
- `IN2.LINE2 = 0`
- `IN2.LINE3 = 0`

Что требуется:
- убрать решение, где “пусто” вычисляется как простое отрицание `batch_ready/program1_active`;
- реализовать одно из двух корректных решений:
  - либо расширить контракт статуса конвейера / верхнего уровня так, чтобы признак `feed_side_empty` задавался по строгому определению;
  - либо ввести отдельный явный атомарный бит или составной статус, который гарантированно соответствует модели `version_4`;
- если без изменения соседнего модуля или протокола это невозможно сделать безопасно, не придумывай эвристику, а верни честный блокер.

3. Исправить recovery-ветку для `step3_ready`

Проблема:
- если восстановление продолжает цикл с шага больше `3`, текущий `step3Ready` может остаться в `0`, хотя правая сторона уже должна считаться освобожденной.

Что требуется:
- при `fromRecovery = true` после безопасной валидации состояния выставлять `step3_ready = 1`, если восстановление продолжается с шага строго позже `3`;
- не делать это слепо: сначала должна быть подтверждена корректность безопасного состояния для такого продолжения;
- если у тебя в коде есть аналогичная логика для шага `7`, проверь ее на ту же проблему;
- не ломай обычный старт нового цикла, где оба latches должны корректно сбрасываться.

4. Проверить верхнюю логику после фиксов

Обязательно перепроверь:
- `pause_requested`
- `pause_fill_last_block`
- `pause_stable_wait`
- обязательную выгрузку из `SEALER`
- ожидание освобождения `OUT2` без новых обычных production-start
- сценарии `30`, `33`, `36`

5. Проверить, что фиксы не утяжелили систему

Нельзя:
- раздувать обмен по `I2C` без необходимости;
- вводить лишние частые опросы;
- добавлять тяжелые проверки в рабочий тик;
- строить ожидания без понятного условия выхода.

Отдельный акцент:
- если логика остается в legacy-модуле, проверь, не создает ли это технический долг или риск, что на железо пойдет другой runtime-контур;
- если это уже отдельный блокер внедрения, назови его прямо.

Формат результата:

- сначала коротко напиши, какие findings закрыты;
- затем перечисли измененные файлы;
- затем напиши, что проверено по коду и сборке;
- если остался блокер, опиши его явно:
  - где он находится;
  - почему он блокирует передачу на железо;
  - что именно нужно решить отдельно.

Важно:
- не переписывай документы ради стиля;
- не подменяй строгую модель `version_4` упрощенной эвристикой;
- если для правильного `feed_side_empty` нужен более честный межплатный контракт, лучше расширить контракт или вернуть блокер, чем оставить ложную “пустоту”;
- если после фиксов код все еще нельзя безопасно передавать на железо, напиши это прямо.
```

## Ожидаемый результат

После работы кодера мы должны получить:

- устраненный блокер по `pause_stable_wait` и `SEALER = EMPTY`;
- корректный и доказуемый контракт `feed_side_empty`;
- корректную recovery-ветку для `step3_ready`;
- либо код, который можно снова отдавать на ревью/перед тестами на железе;
- либо честный список оставшихся блокеров.
