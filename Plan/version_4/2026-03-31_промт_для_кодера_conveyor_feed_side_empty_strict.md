# Промт для кодера: `feed_side_empty_strict` на стороне конвейера

Дата: 2026-03-31

### Назначение

Этот текст нужен для отдельной доработки конвейерной платы и межплатного контракта под строгий `feed_side_empty` по модели `version_4`.

Главная цель:

- убрать оставшийся блокер строгого пути `version_4`;
- перестать вычислять `feed_side_empty` на мастере по эвристике;
- перенести строгий признак пустоты подводящей стороны на саму конвейерную плату;
- отдать мастеру атомарный и безопасный бит для pause-логики и сценариев `30/33/36`.

## Что уже известно

Сейчас ревью подтвердило:

- блокер `pause_stable_wait` закрыт;
- recovery для `step3_ready` закрыт;
- единственный честный блокер сейчас — отсутствие строгого `feed_side_empty`.

Проблема текущей реализации:

- в `archive/firmware/master_control_com12_legacy_2026-03-25/src/master_main.cpp`
  `commonFeedSideEmpty()` сейчас сводится к отрицанию косвенных флагов;
- это не эквивалент строгому определению `version_4`;
- на паузе и в сценарии `33` возможны ложные решения.

## Готовый промт

```text
Ты дорабатываешь конвейерную плату и межплатный контракт под строгий `feed_side_empty` для `version_4`.

Сначала прочитай:
1. `PLSN.md`
2. `Plan/основной_цикл.md`
3. `Plan/сущности_и_состояния.md`
4. все файлы из `Plan/version_4/`
5. `firmware/conveyor_control_com10/src/app/conveyor_status.h`
6. `firmware/conveyor_control_com10/src/app/conveyor_status.cpp`
7. `firmware/conveyor_control_com10/src/app/conveyor_status_runtime.h`
8. `firmware/conveyor_control_com10/src/app/conveyor_status_runtime.cpp`
9. `firmware/conveyor_control_com10/src/comm/i2c_status_provider.h`
10. `firmware/conveyor_control_com10/src/comm/i2c_status_provider.cpp`
11. `firmware/conveyor_control_com10/src/legacy/program1.h`
12. `firmware/conveyor_control_com10/src/legacy/program1.cpp`
13. `firmware/conveyor_control_com10/src/legacy/shift_control.h`
14. `archive/firmware/master_control_com12_legacy_2026-03-25/src/master_main.cpp`

Твоя роль:
- ты не ослабляешь `version_4`;
- ты закрываешь оставшийся честный блокер строгого пути;
- если текущих данных на конвейере недостаточно, ты сначала расширяешь локальный runtime/статус конвейера;
- мастер больше не должен гадать `feed_side_empty` по косвенным флагам.

Строгое определение `feed_side_empty` по `version_4`:

- `BUFFER_COUNT = 0`
- `SHIFT = HOME_Z`
- `IN2.LINE1 = 0`
- `IN2.LINE2 = 0`
- `IN2.LINE3 = 0`

Что нужно сделать обязательно:

1. На стороне конвейера реализовать строгий признак:
- добавить атомарный признак `feed_side_empty_strict`;
- лучше сразу парой:
  - `feed_side_empty_strict`
  - `feed_side_empty_valid`
- `valid = 1` только если признак действительно вычислен по строгой модели, а не по эвристике.

2. Вычисление делать на стороне конвейера, а не на мастере.

3. Если текущий runtime конвейера еще не хранит все нужные компоненты строгого снимка:
- расширить локальный runtime/статус конвейера так, чтобы он умел честно знать:
  - состояние буфера пары (`BUFFER_COUNT` или эквивалентный строгий признак)
  - состояние `SHIFT` как минимум в части `HOME_Z`
  - состояние `IN2.LINE1..LINE3` или эквивалентный строгий снимок накопителя
- не подменять это косвенными признаками вроде только `program1Active` / `batchReady`.

4. Вывести новый признак в межплатный статус:
- без тяжелых текстовых команд;
- без лишнего раздувания обмена;
- через существующий легкий контракт статуса;
- аккуратно выбрать место:
  - либо новый бит в `statusWord`, если там хватает места и это не ломает контракт;
  - либо отдельный бит/поле в `extra*`, если это безопаснее;
- обязательно обновить и конвейер, и мастер одинаково.

5. На стороне мастера:
- убрать эвристику `!batch_ready && !program1_active` как источник истины для `feed_side_empty`;
- перевести `commonFeedSideEmpty()` на новый строгий признак;
- если есть `valid`-бит, мастер не должен использовать строгую пустоту, пока `valid = 0`;
- если `valid = 0`, не придумывай опасную эвристику для паузы: лучше явно оставить блокирующее состояние или честный fallback, который не ломает инварианты `version_4`.

6. После правки обязательно проверить по коду:
- ветки `pause_requested`
- `pause_fill_last_block`
- `pause_stable_wait`
- mandatory unload из `SEALER`
- ожидание освобождения `OUT2`
- сценарии `30`, `33`, `36`

7. Ограничения:
- не утяжеляй рабочий тик без необходимости;
- не раздувай `I2C`;
- не вводи скрытых состояний;
- не оставляй “почти правильный” бит, если он не соответствует строгой модели;
- если строгий признак сейчас нельзя сделать без более глубокого изменения конвейерной логики, не маскируй это: верни честный блокер.

Формат результата:

- сначала коротко напиши, реализован ли строгий `feed_side_empty`;
- затем перечисли измененные файлы;
- затем напиши, где теперь находится новый бит/поле и как он трактуется;
- затем напиши, что проверено по коду и сборке;
- если остался блокер, опиши его прямо:
  - чего именно не хватает на стороне конвейера;
  - почему без этого строгий путь нельзя передавать на железо.

Важно:
- мастер не должен угадывать пустоту подвода;
- источник истины для `feed_side_empty_strict` должен быть на конвейерной плате;
- если нужна дополнительная локальная модель `BUFFER_COUNT / SHIFT / IN2`, лучше честно добавить ее, чем оставить ложную простую эвристику.
```

## Ожидаемый результат

После этой работы мы должны получить:

- строгий атомарный признак `feed_side_empty_strict` на стороне конвейера;
- обновленный межплатный контракт;
- мастера, который больше не гадает пустоту подвода по косвенным флагам;
- либо полностью закрытый последний блокер строгого пути `version_4`;
- либо честное подтверждение, что без более глубокой доработки конвейерного runtime этот блокер пока не закрывается.
