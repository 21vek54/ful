# Архитектура Manual Recovery

Дата: 2026-04-07

## Короткий вывод

Рекомендуемая модель:

- `COMMON` остается строгим production-циклом.
- Любая авария или неясное состояние узла прерывает текущий `COMMON`.
- Продолжение старого `COMMON` после аварии не допускается.
- Выход из аварийного режима идет через отдельный `manual recovery` сценарий оператора.
- После восстановления запускается новый `COMMON START`, а не "resume старого цикла".

## Зачем нужна такая модель

После аварии master обычно не знает достаточно, чтобы безопасно продолжить цикл:

- где сейчас тарелки;
- удержал ли манипулятор блок;
- остался ли блок в запайщике;
- завершился ли отвод;
- какой именно участок механики оказался в промежуточном состоянии.

Поэтому после аварии правильнее:

1. остановить automation;
2. отдать управление оператору;
3. вручную довести каждый затронутый узел до валидного состояния;
4. вернуть систему в `ready`;
5. запустить новый `COMMON START`.

## Базовый контракт

### 1. Что делает master

Master должен:

- прерывать `COMMON` при аварии узла или при production-visible interlock;
- переводить систему в состояние `manual recovery required`;
- показывать оператору последнюю причину abort;
- не пытаться автоматически продолжить старый цикл после самовосстановления узла;
- разрешать новый `COMMON START` только когда все обязательные сущности снова в `ready`.

Master не должен:

- угадывать, можно ли продолжать старый цикл;
- сам выполнять ручное доведение узлов;
- считать кратковременный `alarm`, который уже исчез, доказательством безопасного продолжения.

### 2. Что делают локальные контроллеры

Локальные контроллеры должны:

- сохранять свои coarse-признаки `ready / busy / alarm / recovery required`;
- предоставлять сервисные ручные команды для доведения механики;
- иметь локальные `recovery clear` только там, где это действительно нужно;
- не скрывать от мастера production-visible interlock.

### 3. Что делает оператор

Оператор должен иметь возможность:

- вручную двигать каждый узел;
- выгрузить зависший блок;
- вернуть механику в стартовую позу;
- снять локальный recovery latch после проверки;
- увидеть, какие сущности уже `ready`, а какие еще нет.

## Сущности manual recovery

### Манипулятор

Manual recovery для манипулятора:

- ручные движения по осям;
- ручное открытие/закрытие захвата;
- возврат в безопасную стартовую позу;
- снятие локальной ошибки;
- подтверждение coarse-состояния `ready`.

Если во время `COMMON` у манипулятора был `alarm`, даже если он потом сам снялся, старый цикл не продолжается.

### Подводящий блок

Manual recovery для подвода:

- ручной доворот/досборка/освобождение участка;
- при необходимости синхронизация feed-side модели;
- возврат в coarse-состояние `batch_ready` или понятное `wait`.

### Запайщик

Manual recovery для запайщика:

- ручная проверка механики;
- при необходимости ручная выгрузка;
- локальный `POST7 RECOVERY CLEAR` только после проверки;
- возврат в `ready`, если узел реально безопасен для нового цикла.

### Отводящий блок

Manual recovery для отвода:

- ручной доворот;
- ручная выгрузка хвоста;
- возврат к `outfeed_ready_for_batch = true`.

## Правильный переход состояний

Нормальный путь после аварии:

1. `COMMON active`
2. `alarm / interlock / fault`
3. `COMMON aborted`
4. `manual recovery required`
5. оператор вручную доводит узлы
6. локальные recovery-clear там, где это нужно
7. все обязательные сущности возвращаются в `ready`
8. оператор запускает новый `COMMON START`

Неправильный путь:

- `alarm`
- узел сам восстановился
- master "надеется", что все уже хорошо
- старый `COMMON` сам продолжается

Такой путь опасен, потому что физическое состояние линии уже могло уйти от модели.

## Минимальный UI-контракт

В recovery-режиме HMI должен показывать:

- последнюю причину abort;
- какие сущности еще не восстановлены;
- какие сущности уже `ready`;
- какие ручные действия доступны по каждой сущности;
- отдельный признак `можно запускать новый COMMON` только когда все необходимые узлы готовы.

UI не должен:

- подменять ручное восстановление автоматическим решением;
- прятать корневую причину abort;
- показывать "все хорошо", если хотя бы один recovery latch еще стоит.

## Рекомендуемое решение по текущему проекту

Для текущей архитектуры `fyl` рекомендуется:

- оставить правило `alarm манипулятора => abort COMMON`;
- развивать отдельный recovery-режим оператора;
- дать оператору ручные команды по узлам;
- не делать auto-resume старого `COMMON`;
- после recovery запускать только новый `COMMON START`.

## Что можно делать дальше

Следующие честные шаги:

1. Описать список ручных recovery-команд по каждой сущности.
2. Зафиксировать coarse-признак `system recovery ready`.
3. Переделать HMI так, чтобы была отдельная вкладка `Восстановление`.
4. Отдельно решить, где нужен локальный `clear`, а где достаточно просто возврата в `ready`.
