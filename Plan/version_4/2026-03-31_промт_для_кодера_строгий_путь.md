# Промт для кодера: строгий путь `version_4`

Дата: 2026-03-31

### Назначение

Этот текст нужен для передачи задачи кодеру по строгому пути `version_4`.
Строгий путь означает:

- если текущая прошивка плат расходится с согласованной моделью `version_4`, переписываем логику плат;
- модель `version_4` без отдельного решения не ослабляем;
- `step3_ready` реализуем как реальный признак в прошивке манипулятора, а не как догадку верхнего уровня по одному `current step`.

## Готовый промт

```text
Ты реализуешь строгий путь `version_4` по проекту `fyl`.

Сначала прочитай:
1. `PLSN.md`
2. `Plan/основной_цикл.md`
3. `Plan/сущности_и_состояния.md`
4. все файлы из `Plan/version_4/`
5. `firmware/manipulator_com11/src/work_cycle.h`
6. `firmware/manipulator_com11/src/work_cycle.cpp`
7. `firmware/manipulator_com11/src/main_10.inc`

Твоя роль:
- ты не пересобираешь архитектуру заново;
- архитектурный пакет `version_4` уже принят как целевая модель;
- если текущая логика плат с ней расходится, ты приводишь прошивки к модели, а не наоборот.

Главная цель этой задачи:
- реализовать `version_4` по строгому пути;
- сделать `step3_ready` реальным сигналом из прошивки манипулятора;
- затем опереться на него в верхней логике линии;
- не вводить лишний шум в `I2C`, `CPU`, `RAM` и рабочий тик.

Что нужно сделать обязательно:

1. На стороне прошивки манипулятора:
- ввести реальный runtime-признак `step3_ready`;
- смысл признака зафиксировать так:
  - `step3_ready = 1` только после успешного завершения шага `3`;
  - это означает, что правая сторона манипулятора уже освобождена для логики `IN2`;
  - признак нельзя выводить только по одному `current step`, его нужно выставлять отдельной логикой в прошивке;
- по аналогии с текущим `step7_ready` сделать поведение понятным и устойчивым;
- при старте нового `R`, при ошибке и при сбросе цикла флаг должен сбрасываться в согласованное безопасное состояние;
- обновить `work_cycle.h/.cpp` и экспорт статуса в `main_10.inc`.

2. На стороне `I2C` контракта манипулятора:
- вывести `step3_ready` как отдельный бит в статусе;
- не городить для этого отдельные текстовые команды или тяжелый обмен;
- сохранить текущую легкую модель опроса;
- не ломать существующий `step7_ready`, а дополнить контракт аккуратно.

3. На стороне верхней логики линии:
- найти реальные места, где принимаются решения по `IN2`, `MANIPULATOR`, `SEALER`, `OUT2` и паузе;
- перевести эти решения на согласованную модель `version_4`;
- использовать реальный `step3_ready` там, где по документам нужна ранняя разблокировка подводящей стороны;
- использовать `step7_ready` только с учетом того, что это latch текущей прошивки, а не мгновенный импульс;
- не строить логику на скрытых неописанных состояниях.

4. Обязательно соблюсти правила `version_4`:
- снимки состояния сравнивать в терминах `состояние до тика`, `переходное состояние`, `состояние после тика`, `устойчивое состояние`;
- порядок `тика логики` считать таким:
  - `INFEED -> SHIFT -> IN2 -> MANIPULATOR -> SEALER -> OUT2 -> MAIN_OUT`
- правило same-tick для `IN2` сохранить:
  - после записи пары в `IN2.LINE1` накопитель `IN2` может сделать свой такт в этом же тике;
  - если после записи уже получился полный блок, дополнительный такт в этом же тике не нужен;
- контракт паузы не ослаблять:
  - `pause_requested`
  - `pause_fill_last_block`
  - `pause_stable_wait`
  - обязательный выгрузочный цикл из `SEALER`
  - `pause_stable_wait` допустим только при `SEALER = EMPTY`
- при занятом `OUT2` во время обязательной выгрузки линия ждет освобождения `OUT2` без новых обычных производственных стартов.

5. Ограничения по реализации:
- не увеличивай число опросов без явной необходимости;
- не раздувай `I2C` обмен лишними статусами;
- не утяжеляй рабочий тик дорогими проверками;
- не вводи бесконечные ожидания без явного таймаута или понятного условия выхода;
- не делай частичных архитектурных костылей, которые потом придется вычищать.

6. Проверка после реализации:
- собрать код;
- проверить, что новый контракт `step3_ready` компилируется и реально доступен верхнему уровню;
- проверить, что `step7_ready` не сломан;
- сверить код с эталонными сценариями `30`, `33`, `36`;
- отдельно проверить ветки паузы;
- если полной аппаратной проверки нет, явно написать, что проверено только на уровне кода и сборки.

Формат результата:

- сначала коротко напиши, что именно реализовано;
- затем перечисли измененные файлы;
- затем напиши, что проверено;
- если нашел архитектурный блокер, не маскируй его:
  - опиши, где блокер;
  - почему он блокирует строгий путь;
  - что именно нужно решить отдельно.

Важно:
- не переписывай документы ради стиля;
- не ослабляй `version_4`, чтобы подогнать ее под текущую прошивку;
- если для строгого пути нужно менять прошивку манипулятора, меняй ее;
- если для строгого пути нужно менять верхнюю логику линии, меняй ее;
- если обнаружишь, что без отдельного решения модель в код не переносится безопасно, остановись и верни findings, а не делай скрытую упрощенную версию.
```

## Ожидаемый результат

После работы кодера мы должны получить:

- реальный `step3_ready` в прошивке манипулятора;
- обновленный `I2C` контракт без лишнего утяжеления;
- верхнюю логику линии, опирающуюся на согласованную модель `version_4`;
- либо цельную реализацию строгого пути;
- либо честный список блокеров, если строгий путь упрется в отдельное техническое ограничение.
