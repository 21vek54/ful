# Промт для кодера: минимизация `I2C`-контракта между мастером и манипулятором

Дата: 2026-04-06

### Назначение

Этот текст нужен для передачи кодеру задачи по упрощению и минимизации рабочего `I2C`-контракта между:

- legacy master `COM12`
- manipulator `COM11`

Главный смысл:

- не ломать текущий `COMMON`;
- не перепридумывать архитектуру всей линии;
- убрать лишнюю связанность мастера с сырыми внутренними деталями манипулятора;
- оставить только тот контракт, который реально нужен верхней логике линии.

Важно:

- речь идет о фактическом runtime-контуре;
- верхняя логика `COMMON` сейчас живет не в новом минимальном `firmware/master_control_com12`, а в:
  - `archive/firmware/master_control_com12_legacy_2026-03-25/src/master_main.cpp`

Новый минимальный master сейчас трогать не нужно, если это не требуется отдельно.

## Контекст

По текущему коду:

- master опрашивает манипулятор статусным `I2C`-кадром;
- во время `COMMON` master шлет манипулятору текстовые команды по `I2C`;
- реально в `COMMON` используются только:
  - `R`
  - `Q`
- при этом master сейчас читает и использует:
  - `busy`
  - `step3_ready`
  - `step7_ready`
  - сырые sensor bits для определения стартовой позы
  - косвенные детали из `extra`-полей

Сейчас проблема не столько в размере кадра, сколько в том, что верхняя логика завязана на слишком низкоуровневые детали манипулятора.

Цель этой задачи:

- минимизировать именно обязательный runtime-контракт;
- сделать его более смысловым и устойчивым;
- при этом не ломать текущий `COMMON` и не раздувать `I2C`.

## Целевой минимальный контракт

Для production-ветки `COMMON` между master и manipulator нужно оставить по минимуму:

### Команды master -> manipulator

- `R` — запустить рабочий цикл
- `Q` — открыть захват, если нужно только это для входа в стартовую позу

### Статусы manipulator -> master

Master в `COMMON` должен зависеть только от таких смысловых признаков:

- `busy`
- `fault` / `alarm`
- `work_start_ready`
- `needs_grip_open_only`
- `step3_ready`
- `step7_ready`

Смысл флагов:

- `work_start_ready = 1`
  - манипулятор находится в полной рабочей стартовой позе:
  - право
  - верх
  - захват открыт

- `needs_grip_open_only = 1`
  - манипулятор уже в позе:
  - право
  - верх
  - но захват еще не открыт
  - то есть master может отправить только `Q`, а не считать это полной неготовностью

- `step3_ready = 1`
  - правая сторона освобождена для раннего продолжения линии

- `step7_ready = 1`
  - достигнута ранняя точка синхронизации после шага `7`

При этом:

- raw sensor bits можно временно оставить в кадре для диагностики и обратной совместимости;
- но верхняя логика `COMMON` не должна больше опираться на них напрямую, если новые смысловые биты уже есть;
- `current step`, `job code`, `mode code`, conflict bits не должны оставаться обязательными для логики `COMMON`, если они нужны только для диагностики.

## Готовый промт

```text
Ты дорабатываешь проект `fyl`.

Твоя задача:
- минимизировать рабочий `I2C`-контракт между legacy master и manipulator;
- убрать лишнюю зависимость верхней логики `COMMON` от сырых sensor bits манипулятора;
- сохранить текущий рабочий сценарий `COMMON`;
- не раздувать `I2C`, не добавлять новые лишние команды и не утяжелять polling.

Сначала прочитай:
1. `PLSN.md`
2. `Plan/основной_цикл.md`
3. `Plan/сущности_и_состояния.md`
4. `Plan/version_4/2026-04-06_промт_для_кодера_минимизация_i2c_контракта_манипулятора.md`
5. `firmware/manipulator_com11/src/main_10.inc`
6. `firmware/manipulator_com11/src/work_cycle.h`
7. `firmware/manipulator_com11/src/work_cycle.cpp`
8. `archive/firmware/master_control_com12_legacy_2026-03-25/src/master_main.cpp`

Твоя роль:
- ты не переносишь `COMMON` в новый minimal master;
- ты работаешь с фактическим runtime-контуром;
- верхняя логика `COMMON` сейчас живет в legacy master, и именно ее нужно привести к более чистому контракту;
- нельзя ломать текущую механику линии ради "красоты" контракта.

Главная цель:
- для production-ветки `COMMON` master должен зависеть только от:
  - `busy`
  - `fault` / `alarm`
  - `work_start_ready`
  - `needs_grip_open_only`
  - `step3_ready`
  - `step7_ready`
- команды production-уровня от master к manipulator должны остаться только:
  - `R`
  - `Q`

Что нужно сделать обязательно:

1. На стороне manipulator ввести смысловые биты готовности стартовой позы

Нужно:
- добавить в статус manipulator два явных runtime-флага:
  - `work_start_ready`
  - `needs_grip_open_only`
- вычислять их на стороне manipulator по реальным локальным sensor bits;
- смысл зафиксировать строго:
  - `work_start_ready = 1`, только если:
    - right limit active
    - Z up active
    - grip open active
  - `needs_grip_open_only = 1`, только если:
    - right limit active
    - Z up active
    - grip open inactive
- эти флаги должны быть взаимоисключающими в нормальном случае;
- если состояние конфликтное или unsafe, лучше вернуть оба в `0`, чем угадывать.

2. Не ломать существующие `step3_ready` и `step7_ready`

Нужно:
- сохранить текущий runtime-latch подход для:
  - `step3_ready`
  - `step7_ready`
- не заменять их эвристикой по одному `current step`;
- не ломать recovery-ветки и не ломать сброс latches в начале нового `R`.

3. На стороне legacy master перевести `COMMON` на новый минимальный смысловой контракт

Нужно:
- найти места, где `COMMON` принимает решения по manipulator;
- убрать зависимость production-логики от сырых sensor bits manipulator там, где это уже можно заменить смысловыми флагами;
- использовать:
  - `work_start_ready`
  - `needs_grip_open_only`
  - `busy`
  - `step3_ready`
  - `step7_ready`
- текущую логику оставить такой:
  - если `work_start_ready = 1`, master может сразу слать `R`
  - если `needs_grip_open_only = 1`, master может слать `Q`, затем ждать полной готовности и слать `R`
  - если оба флага `0`, master должен считать, что manipulator не готов к обычному production-start

4. Не раздувать низкоуровневый `I2C`

Нельзя:
- вводить новые текстовые production-команды, кроме уже существующих `R` и `Q`
- увеличивать частоту polling без отдельной причины
- вводить дополнительные запросы "на всякий случай"
- делать тяжелую синхронизацию через частый текстовый обмен

Важно:
- если возможно, оставь размер кадра прежним и не ломай совместимость диагностики;
- минимизация в этой задаче означает прежде всего минимизацию обязательного контракта верхней логики, а не обязательное физическое уменьшение размера кадра любой ценой.

5. Не ломать текущую диагностику без причины

Если raw поля:
- sensor bits
- current step
- job code
- mode code

сейчас еще используются в логах, MQTT или отладке, ты можешь временно оставить их в кадре.

Но:
- `COMMON` не должен дальше зависеть от них напрямую, если уже есть новые смысловые биты;
- если какое-то поле остается только ради диагностики, это стоит явно обозначить в результате.

6. Проверка после изменений

Обязательно проверь:
- manipulator компилируется;
- legacy master компилируется;
- `COMMON` path по коду сохраняет текущий смысл:
  - poll status
  - если нужно, `Q`
  - затем `R`
  - ожидание `step3_ready`
  - ожидание `step7_ready`
  - ожидание завершения цикла
- нет лишних новых `I2C` команд;
- master больше не зависит в production-логике от raw sensor bits там, где уже может использовать смысловые флаги.

Формат результата:

- сначала коротко напиши, что именно изменено в контракте;
- затем перечисли измененные файлы;
- затем отдельно перечисли:
  - какие поля теперь обязательны для `COMMON`
  - какие поля остались только для диагностики
- затем напиши, что проверено;
- если нашел блокер, напиши его прямо:
  - где он находится
  - почему без него нельзя честно ужать контракт дальше

Важно:
- не переноси верхнюю логику в новый minimal master;
- не убирай `Q`, если без него ломается мягкая подготовка стартовой позы;
- не ломай `step3_ready` / `step7_ready`;
- не строй новую эвристику по raw sensor bits там, где можно дать смысловой бит;
- если для следующего шага можно еще сильнее ужать кадр, но это уже отдельная безопасная фаза, не смешивай это с текущей задачей.
```

## Ожидаемый результат

После работы кодера мы должны получить:

- смысловой минимальный контракт master ↔ manipulator для `COMMON`;
- production-ветку, завязанную только на нужные признаки;
- сохраненные команды `R` и `Q` как единственные production-команды к манипулятору;
- отсутствие лишнего раздувания `I2C`;
- либо честно реализованную минимизацию;
- либо явный список блокеров, если дальше безопасно ужать контракт без второй фазы нельзя.
